# AppIcon 设计规范

**当前版本 v3.0（2026-09-25）** —— 纸白底 + 一台墨色**两厢**侧影，无文字，浅色 / 深色 / 着色三套外观。
出包的那份永远由 `generate_appicon_pillow.py` 渲染；`AppIcon.svg` 只是矢量对照。

---

## 一、这一版是怎么来的：一轮 100 个方向，用户挑了 040

v2.x 修掉了「不符合 iOS 调性」的**规**（见下一节的四条），但仍然是我一个人定的构图。
于是做了一轮**探索稿**：100 个 1024 方案，同一套几何换容器、换底色、换画法、
换主体（`design-preview/icon-100.html`，自包含 base64 单页；**那张稿子选完就删了**，见本节末），用户在真机 / 浏览器里看，
报了一个编号回来。

**他挑的是 040「两厢 · 纸白底」** —— 一张探索稿里没有名字、也没有倾向的条目，
选中它的理由不需要我替他总结。v3.0 就是把 040 折进正式渲染器：

- 车形换成**两厢**（探索稿里的 `hatch`），底换成**纸白**，车身从白换成**墨色**；
- v2.1 那道「车底下的路」（`ARC_*`）**删掉** —— 040 里没有它；
- 探索稿用完即弃：`icon-100.html` / `icon-20.html` 与两个生成脚本已随这一版删掉
  （它们的 docstring 本来就写着「用完即弃，或用户选定后把中选的那个折进
  `generate_appicon_pillow.py`」）。**留下来的只有中选的那一张**，这是这个仓库对
  「挑完了」的一贯做法 —— 留着 100 个方案，下一个人改图标时不知道以哪个为准。

**折进来时做过逐点比对**（同一张 1024、同一套画法，本版 vs 探索稿 040）：

| 量 | 结果 |
|---|---|
| 完全相同的像素 | **99.76%** |
| 有差异的 | 8.79%（全部 ≤ 8 色阶） |
| 差 > 8 的 | **0.24%** —— 全落在 1px 宽的车身边缘上，来自常数取整（映射原值写进去则是 0 处差异） |

比对顺带查出一个**真的参数错**：柔影的位移在探索稿里是 `int(1024 × 0.022) = 22`，
我先写成 23 —— 量出来 23 时有 89485 个像素有差（最大 2），22 时只有 174 个（最大 1）。
眼睛看不出来，数字看得见；`SHADOW_DY` 的注释里记着这条。

## 二、v2.x 到底改对了什么（四条，每条都能量出来）

用户上一轮的原话是「完全不符合 iOS 调性、太丑了」。「调性」听着主观，但 v1.0 之所以必须整张重画，
是因为它犯了四条**可以指着像素说清**的错 —— 它们全部编译得过、当时 31 条门禁全绿、
模拟器里也完全正常，所以没有任何自动检查看得见它们：

| # | v1.0 的问题 | 实测证据 | 现在的做法（v2 / v3 一致） |
|---|---|---|---|
| ① | **底色近黑** | 1024 主图亮度 p05 / p50 / p95 = **0.000 / 0.096 / 0.659** —— 深蓝黑 `#1A1A2E→#0D0D1A` 在主屏上就是一块黑 | 亮底。v3 是纸白 `#F9FAFC→#E2E7F0`，p05 / p50 / p95 = **0.136 / 0.916 / 0.980**。iOS 的图标语言是「亮底 + 一个物体」，旧图正好反过来 |
| ② | **图上有字** | 「长安车管家」+「CHANGAN CONNECT」两行，占画面下缘约一成高 | 一个字都没有。Apple 图标规范第一条就是不要放文字 —— 29pt 下那两行是两团灰噪点 |
| ③ | **自己套圆角 / 内缩 4%，且四角是纯黑** | 生成脚本最后 `convert('RGB')` 把透明边压成了 **纯黑 (0,0,0)**；左右边缘中点 = (0,0,0)，而同行内侧 = (255,159,0)，**色差 255**。系统还会再套一层 squircle，成品因此比邻居小一圈、遮罩里还留四个黑角 | **满幅**：1024×1024 铺满，图里不画圆角、不留边、不留透明（模式就是 `RGB`，没有 alpha 通道）。圆角由系统裁。实测 8 个采样点（四角 + 四边中点）边缘与内侧相隔 64px 的最大色差 = **1 / 4 / 5**（浅色 / 深色 / 着色，门禁上限 14） |
| ④ | **没有深色 / 着色外观** | 7 个槽位全是同一张浅色图 | 7 槽位 × 浅色 / 深色 / 着色 = **21 张**。iOS 18 起主屏有这三种图标外观，只给一张，系统只能把同一张往深色与着色里硬套 |

**四角黑角是 ③ 里最实的一条**：v1.0 的图看起来是「圆角已好」，其实是 `convert('RGB')` 把
本该透明的边压成了黑，于是系统遮罩内部又叠了一个黑框。v2.x 直接把整张铺满，
`scan/iconcheck.py` 的判据 4 就是照着这一条写的：**四角与同一行内侧（相隔 64px）的颜色必须一致**。

## 三、设计理念

四句话，每句都能指着脚本里的一段代码：

1. **亮底** —— 纸白竖向渐变（`#F9FAFC → #E2E7F0`）。亮底 + 一个深色物体，
   是 iOS 图标语言里最稳的一种搭配。
2. **一个物体** —— 墨色（`#161A22`）两厢侧影。窗与轮拱是**挖空**（透出底色，
   不是画一块深灰），没有描边、没有贴图感。
3. **一层柔影 + 一层顶光** —— 影子是同一张形状下移 22px、模糊 18、压 30% 黑；
   顶光是一道 0.12 的渐隐白。这两样就是 040 的 `gloss + shadow` 画法：
   影子给「离底一点点距离」，顶光给 iOS 26 那层「玻璃表面」，没有它纯渐变会显得平。
4. **没有第二层装饰** —— v2.1 那道车底下的弧（续航圈的图形引用）**这一版没有**：
   用户挑的 040 里没有它。往一个被挑中的图里加东西，就是换一种方式不认账。

## 四、三套外观（`APPEARANCES`，数值以脚本为准）

| 外观 | 底（上→下） | 车 | 柔影 | 顶光 |
|---|---|---|---|---|
| `light`（无 `appearances` 字段） | `(249,250,252)` → `(226,231,240)` | 墨 `(22,26,34)` | 0.30 | 0.12 |
| `dark` | `(46,36,24)` → `(16,13,10)` | 白 `(255,255,255)` | 0.30 | 0.12 |
| `tinted` | `(126,126,132)` → `(62,62,68)` | 白 `(255,255,255)` | 0.30 | 0.08 |

- **深色外观必须换图形，不只是换底**：墨色的车放到暖近黑底上等于没有车。
  判据是**亮度**：车身亮度 < 128 → 深色下转白（探索稿的 `dark_preview` 就是这个规则，
  v3 沿用）。深色底用的是 App 自己那套夜间配色。
- **着色外观只给灰阶**：系统是按**亮度**上色的，给彩色只会被压平 —— 这是 iOS 的处理方式，
  不是偷懒。底偏暗而不是偏亮：着色外观下整张图会被上一层色，亮底会变成一大块实色。

## 五、几何（脚本里的常量，单位是 1024 坐标系）

```
CAR      = (45,789)(45,612)(101,512)(232,346)(512,313)(680,368)(811,490)(904,534)(979,623)(979,789)
WHEELS   = (236,720) (778,720)      WHEEL_R = 135     HUB_R = 49
WINDOWS  = (283,376,484,484) (526,376,680,484)        WINDOW_R = 29
ROUND_PX = 21      HOLE_BLUR = 6
SHADOW   = 位移 (6,22)   模糊 18   浓度 0.30
```

这一组数是**映射出来的，不是画出来的**：探索稿把车写在 0…1 的方框里
（`frac = 0.60 × 1.52 = 0.912`，长高比 `0.593`）再映到 1024 —— 于是同一个形状在 100 个
方向里能换容器、换尺寸而不改一个数。折进来时把映射结果写成常数（保留 1024 这一个坐标系），
并逐点比对过（见第一节）。

**实测占位**（量的是渲染出来的 mask，不是估的）：车身 **935 × 473**（长高比 **1.98**），
占画布**宽 91.3% / 高 46.2%**，覆盖 **22.6%** 面积。v2.1 是 689 × 409（67% / 40%）——
这一版的车更宽也更扁，这是两厢侧影本身的比例，不是又放大了一轮。

四条**约束**（都注明在脚本里，改形状时先看它们）：

- **轮毂必须整个落在车身内**：`cy + HUB_R ≤ 车底线（789）`，实测 720 + 49 = **769**（余量 20）。
  超出的那一刻，补回来的轮心就会飘在底色上（v2.0 实测过：`cy=700, R=84` 时每个轮子下面露出 32 单位）。
- **轮拱是开口，不是洞**：轮胎圆（`r=135`）下半截**故意落在车身底边之外**（720 + 135 = 855 > 789），
  于是轮拱朝地面敞开 —— 这才是真车的样子。它做的是「挖空」，挖不到的地方本来就不存在，
  所以这里不需要「圆必须装进车身」那条约束（v2.1 的车是封底的，那条约束属于它）。
- **窗必须落在车厢内部**（车身折线在每个 y 上的左右边界之间），否则会在车身边上咬出缺口。
  y=430 处车厢大约跨 x 250…700，所以窗排到 283…680；两扇之间的 B 柱留 **42**
  （58pt 下约 2.4px，再窄缩小时就糊成一扇）。
- **圆角用「高斯模糊 + 阈值」做，不手写圆弧**：纯 Pillow 里写贝塞尔代价大，而这一步的效果
  就是「几何但有肉」（`ROUND_PX = 21`）。窗与轮拱也走同一条路（`HOLE_BLUR = 6`）。

改形状只改这几个常量，**并且要同步改 `AppIcon.svg`**（两者是同一套几何，SVG 只是给人看的对照）。

## 六、尺寸规格

### 导出尺寸（与 `Contents.json` 一一对应）

**7 个槽位 × 3 套外观 = 21 个文件**，文件名规则：浅色就是原名，其余带后缀
（`AppIcon-60x60@2x-dark.png` / `AppIcon-60x60@2x-tinted.png`）。

| 文件名 | 像素 | 用途 |
|--------|------|------|
| `AppIcon-1024x1024.png` | 1024×1024 | App Store 提交；其余机型尺寸由 Xcode 从它生成 |
| `AppIcon-60x60@2x.png` | 120×120 | iPhone 主屏幕 |
| `AppIcon-60x60@3x.png` | 180×180 | iPhone 主屏幕 (Retina HD) |
| `AppIcon-29x29@2x.png` | 58×58 | 设置 / Spotlight |
| `AppIcon-29x29@3x.png` | 87×87 | 设置 / Spotlight (Retina HD) |
| `AppIcon-40x40@2x.png` | 80×80 | Spotlight |
| `AppIcon-40x40@3x.png` | 120×120 | Spotlight (Retina HD) |

**没有 `1x` 槽位，也没有 iPad 专属槽位 —— 这两条都不是遗漏。**

- 目标系统是 iOS 26（`TARGETED_DEVICE_FAMILY: 1,2`），能装它的机型**全是 @2x / @3x**，
  `1x` 槽位没有任何消费者。
- 一张 1024 就够。Apple《Configuring your app icon using an asset catalog》原文：
  「iOS, iPadOS, tvOS, and watchOS apps can auto-generate all icon variations from a
  single 1024×1024 pixel image」，同一页还写「if you have an existing project that
  provides multiple variants, consider providing a single size when that is all your
  icon requires」。
- iPad 图标现在就是这么来的：构建日志里的
  `assetcatalog_output/thinned/AppIcon76x76@2x~ipad.png` 是 Xcode 自己从 1024 生成的。

### 为什么不能写 `idiom: "ipad"`

`Contents.json` 里其它条目是 `idiom: "universal"` + `platform: "ios"`；凡是写成
`idiom: "ipad"` 的，actool 会记进 **「AppIcon has N unassigned children」**，N 正好等于
这类条目的个数 —— 也就是说它们**被忽略**。四个提交里的对应关系：

| 提交 | 条目 | 其中 `idiom: "ipad"` | 1x 槽位 | CI 实测 N |
|------|-----|----------------------|---------|-----------|
| `63decaa` | 12 | 3 | 3 | 3 |
| `ad02a88` | 9 | 2 | 0 | **2** |
| `fe4e36f` | 9 | 2 | 0 | 2 |
| `28b9e1b` | 10 | 3 | 1 | 3 |

`ad02a88` 那一步是判决点：那一轮把**三个 `1x` 槽位全部删掉**，若成因是 1x，N 应归 0；
它却只是 3 → 2，正好剩两条 `ipad` —— 所以成因是 `idiom`，不是 1x。`63decaa` 时两种
解释都恰好等于 3，这正是当初误判成「1x 槽位」的原因（见 `REDESIGN-STATUS.md` §10.6）。

三套外观的写法（2026-09-25 起）：同一槽位追加三个条目，深色 / 着色那两条多一个
`"appearances":[{"appearance":"luminosity","value":"dark"|"tinted"}]`，`filename` 指向带后缀的 PNG。
这个格式是照着**真实 Xcode 生成的 appiconset** 核的，不是照印象写的。

## 七、生成方法

### 唯一入口

```bash
# 依赖只有 Pillow（不需要 ImageMagick / cairosvg）
pip3 install Pillow
bash generate_appicon.sh
```

`generate_appicon.sh` 一条命令做两件事：① 用 `generate_appicon_pillow.py` 渲染 21 张，
直接写进**出包的那份** appiconset；② 顺手跑 `python3 scan/iconcheck.py` 自查（PNG 与
`Contents.json` 是否还一致）。

> **为什么只剩 Pillow 这一条路**（2026-09-25 改）：上一版先找 ImageMagick、找不到再退回
> `python3 generate_appicon.py` —— 而**那个文件根本不存在**。也就是说，文档承诺的退路是一条死路，
> 而它只有在「这台机器没有 ImageMagick」时才会被走到。更根本的是：ImageMagick 只能渲 SVG，
> 而 SVG 里只有浅色一套外观 —— 用它刷新会得到「一半是新图、一半是旧图」的图标集，
> 正是这个仓库记过的那个坑（**改了 A、真机上看到 B**）。所以现在 SVG 只是矢量对照，
> 出包的那一份永远由 Pillow 脚本渲染。

### 关于 `AppIcon.svg`

`AppIcon.svg` 是 v3.0 的**矢量对照**，不是可出包的源：它只有浅色一套外观，也没有深色 / 着色。
它存在的意义是「想看清几何时有一张能缩放的图」；任何一个形状常量改了，两边都要改。
（两处**已知的近似**：车身圆角在脚本里是「模糊 + 阈值」，SVG 里用 `stroke-linejoin="round"`
近似；柔影在脚本里是整张画布偏移后模糊，SVG 的滤镜区域会在边缘收一点。）

### 放置位置

```
CarKeeper/CarKeeper/Resources/Assets.xcassets/AppIcon.appiconset/
```

**只有这一份 appiconset 会进包。** 仓库根目录历史上出现过的另一份 `AppIcon/` 已删 ——
两份并存时，改了不出包的那一份，谁都看不出来。这也是 `scan/iconcheck.py` 判据 5
（「目录里不许有没人引用的 PNG」）的由来。

## 八、圆角规范

iOS AppIcon 用 Squircle（超级椭圆）圆角遮罩，**由系统添加**。

- 图里**不要**自己画圆角、不要内缩、不要留透明边 —— 你自己裁一刀，系统还会再裁一刀，
  成品会比旁边系统图标小一圈。
- 也不要在边上留 4% 的空白：那是 macOS 图标的习惯，不是 iOS 的。
- 唯一要做的就是把 1024×1024 铺满，模式给 `RGB`。

---

## 九、门禁：`scan/iconcheck.py`

图标不是 Swift 文件，`design` / `lintcfg` / `eol` 那些检查一条都看不到它 —— 所以单独立了一条。
五条判据，每条都当场能量出来，不靠眼睛：

1. `Contents.json` 能解析，且每个条目引用的文件真的在目录里。
2. 每个条目的**实际像素尺寸**等于它声明的大小 × scale（1024 槽位视为 1024²）。
3. 每个槽位有**三套外观**：不带 `appearances`（浅色）、`dark`、`tinted`。
4. 三张 1024 主图**满幅**：不带透明像素，且 8 个采样点（四角 + 四边中点）与各自同一行 /
   列内侧相隔 64px 处的颜色一致（上限 `EDGE_TOL = 14`）。为什么是 14 而不是 0：
   底是**渐变**，沿一条边向内 64px 本来就会变色（实测这三套底最多差 **5**），
   而 v1.0 那种内缩 4% 的图一量就是几十、四角干脆是 255。
5. 目录里没有**没人引用**的 PNG（多出来的那种文件正是「改了 A 看到 B」的来源）。

> **这条门禁为什么自己读 PNG，而不是 `import PIL`**（值得记下来）：
> 门禁都住在 `scan/`，而脚本所在目录会被放进 `sys.path`。`scan/copy.py`（文案门禁）
> 与标准库的 `copy` **同名** —— Pillow 的 XML 依赖（`defusedxml` → `xml.etree`）
> 一 `import copy` 就拿错了模块，当场 `AttributeError: module 'copy' has no attribute 'deepcopy'`。
> 也就是说：**任何在 `scan/` 里 import Pillow 的门禁都跑不起来**。
> 所以 `iconcheck.py` 自己读 PNG（zlib + 五种过滤器，只认 8-bit RGB/RGBA、非交错 ——
> 我们自己的生成器只写这一种；其它格式一律报红让人来看，不静默放行）。
> 这个解码器与 Pillow 做过逐点比对（3 张主图 × 9 个采样点，结果一致）。

## 十、视觉检查清单

- [ ] 1024×1024 主图清晰，**满幅无黑角**
- [ ] 车身是**两厢**：长高比约 1.98、占画布宽 91%、后部立着（C 柱那两折看得出）
- [ ] 窗与轮拱是**挖空**（透出底色，不是画深色块），轮拱朝地面敞开
- [ ] 轮毂完整落在车身内（`cy + HUB_R ≤ 789`），洞里有轮芯
- [ ] 柔影在车身下偏右下、顶光在顶部，两者都不压出硬边
- [ ] 三套外观（浅色 / 深色 / 着色）都在，且深色下**车是白的**（墨车在近黑底上等于没有车）
- [ ] 58px 下仍读得出是一台车（窗、轮拱、轮毂不糊成一团）
- [ ] 所有尺寸变体无失真
