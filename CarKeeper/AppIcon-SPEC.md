# AppIcon 设计规范

**当前版本 v2.1（2026-09-25）** —— 满幅亮底 + 一台白色轿车，无文字，浅色 / 深色 / 着色三套外观。
出包的那份永远由 `generate_appicon_pillow.py` 渲染；`AppIcon.svg` 只是矢量对照。

---

## 一、v2.x 到底改了什么（四条，每条都能量出来）

用户的原话是「完全不符合 iOS 调性、太丑了」。「调性」听着主观，但这一版之所以必须整张重画，
是因为 v1.0 犯了四条**可以指着像素说清**的错 —— 它们全部编译得过、当时 31 条门禁全绿、
模拟器里也完全正常，所以没有任何自动检查看得见它们：

| # | v1.0 的问题 | 实测证据 | v2.x 的做法 |
|---|---|---|---|
| ① | **底色近黑** | 1024 主图亮度 p05 / p50 / p95 = **0.000 / 0.096 / 0.659** —— 深蓝黑 `#1A1A2E→#0D0D1A` 在主屏上就是一块黑 | 亮琥珀→橙渐变，p05 / p50 / p95 = **0.561 / 0.718 / 0.957**。iOS 的图标语言是「亮底 + 一个物体」，旧图正好反过来 |
| ② | **图上有字** | 「长安车管家」+「CHANGAN CONNECT」两行，占画面下缘约一成高 | 一个字都没有。Apple 图标规范第一条就是不要放文字 —— 29pt 下那两行是两团灰噪点 |
| ③ | **自己套圆角 / 内缩 4%，且四角是纯黑** | 生成脚本最后 `convert('RGB')` 把透明边压成了 **纯黑 (0,0,0)**；左右边缘中点 = (0,0,0)，而同行内侧 = (255,159,0)，**色差 255**。系统还会再套一层 squircle，成品因此比邻居小一圈、遮罩里还留四个黑角 | **满幅**：1024×1024 铺满，图里不画圆角、不留边、不留透明（模式就是 `RGB`，没有 alpha 通道）。圆角由系统裁。实测 8 个采样点（四角 + 四边中点）边缘与内侧的最大色差 = **7**（门禁上限 14） |
| ④ | **没有深色 / 着色外观** | 7 个槽位全是同一张浅色图 | 7 槽位 × 浅色 / 深色 / 着色 = **21 张**。iOS 18 起主屏有这三种图标外观，只给一张，系统只能把同一张往深色与着色里硬套 |

**四角黑角是 ③ 里最实的一条**：v1.0 的图看起来是「圆角已好」，其实是 `convert('RGB')` 把
本该透明的边压成了黑，于是系统遮罩内部又叠了一个黑框。v2.x 直接把整张铺满，
`scan/iconcheck.py` 的判据 4 就是照着这一条写的：**四角与同一行内侧（相隔 64px）的颜色必须一致**。

## 二、设计理念

三句话，每句对应上面一条：

1. **亮底** —— 琥珀→橙的竖向渐变，是这套图标语言的地基。
2. **一个物体** —— 白色（深色外观下是琥珀色）轿车侧影，窗与轮拱是**挖空**（透出底色，不是画一个深色块），
   没有描边、没有阴影、没有光晕、没有贴图感。
3. **一层高光** —— 顶部一道很淡的白色渐变。iOS 26 的玻璃表面在图标上就是这么一层；
   没有它，纯渐变会显得平（旧图是靠一圈光晕做出「立体感」，那是插画的做法，不是系统图标的做法）。

外加一条图形引用：车身底下那道**向下弯的弧** ＝ App 里「车钉外面那圈弧」（续航圈 / 路径）的引用。
圆心落在车身上、只取下面一段，两端向上收、中间最低，读起来是「地面 / 道路」，而不是一个包围盒。

## 三、三套外观（`APPEARANCES`，数值以脚本为准）

| 外观 | 底（上→下） | 车 | 弧浓度 | 顶部高光 | 底部压暗 |
|---|---|---|---|---|---|
| `light`（无 `appearances` 字段） | `(255,197,61)` → `(255,118,26)` | 白 `(255,255,255)` | 0.22 | 0.16 | 0.10 |
| `dark` | `(46,36,24)` → `(16,13,10)` | 琥珀 `(255,179,71)` | 0.18 | 0.05 | 0 |
| `tinted` | `(126,126,132)` → `(62,62,68)` | 白 `(255,255,255)` | 0.20 | 0.08 | 0 |

- 深色外观的琥珀车就是 App 自己那套夜间配色，`#FF9F00` 是品牌主色。
- **着色外观只给灰阶**：系统是按**亮度**上色的，给彩色只会被压平 —— 这是 iOS 的处理方式，不是偷懒。

## 四、几何（脚本里的常量，单位是 1024 坐标系）

```
CAR      = (180,780)(180,690)(248,612)(368,496)(470,372)(640,372)(722,470)(804,552)(852,580)(868,690)(868,780)
WHEELS   = (320,684) (740,684)      WHEEL_R = 96      HUB_R = 34
WINDOWS  = (455,425,545,515) (575,425,665,515)       ROUND_PX = 16
ARC      = 圆心 (524,700)  半径 250  线宽 26  张角 30°…150°
```

**实测占位**（量的是渲染出来的 1024 主图，不是估的）：车身 **689 × 409**（长高比 1.68），
占画布**宽 67% / 高 40%**；连同底下那道弧，图形整体到画布**高 93%**，覆盖 14.5% 面积。
v2.0 的车只有 300 高、占 29% —— 缩到主屏就是「中间一条小车、四周全是底」，
v2.1 因此把它放大到只留一圈呼吸位。

四条**约束**（都注明在脚本里，改形状时先看它们）：

- **轮心必须满足 `cy + R ≤ 车底线(780)`**。超出的那一刻，车身的轮拱挖空挡不住轮子，
  轮毂会从车底探出来飘在底色上（v2.0 实测过：`cy=700,R=84` 时每个轮子下面露出 32 单位）。
- **窗必须落在车厢内部**（车身折线在每个 y 上的左右边界之间），否则会在车身边上咬出缺口。
  y=425 处车厢跨 x≈430…680，所以窗排到 665；两扇之间的 B 柱留 30（58pt 下约 1.7px，再窄就糊成一扇）。
- **圆角用「高斯模糊 + 阈值」做，不手写圆弧**：纯 Pillow 里写贝塞尔代价大，而这一步的效果
  就是「几何但有肉」（`ROUND_PX = 16`）。
- **弧不能穿过车轮、也不能贴到画布边**：穿过就和两个形状糊在一起，贴边会被 squircle 遮罩的圆角切掉。
  半径 250 让它落在车底线之下再让出 45，最低点 y=950（离画布下边还有 74）。

改形状只改这几个常量，**并且要同步改 `AppIcon.svg`**（两者是同一套几何，SVG 只是给人看的对照）。

## 五、尺寸规格

### 导出尺寸（与 `Contents.json` 一一对应）

**7 个槽位 × 3 套外观 = 21 个文件**，文件名规则：浅色就是原名，其余带后缀
（`AppIcon-60x60@2x-dark.png` / `AppIcon-60x60@2x-tinted.png`）。

| 文件名 | 像素 | 用途 |
|--------|------|------|
| `AppIcon-1024x1024.png` | 1024×1024 | App Store 提交；其余机型尺寸由 Xcode 从它生成 |
| `AppIcon-60x60@2x.png` | 120×120 | iPhone 主屏幕 |
| `AppIcon-60x60@3x.png` | 180×180 | iPhone 主屏幕 (Retina HD) |
| `AppIcon-29x29@2x.png` | 58×58 | 设置 / Spotlight |
| `AppIcon-29x29@3x.png` | 87×87 | 设置 / Spotlight (Retina HD) |
| `AppIcon-40x40@2x.png` | 80×80 | Spotlight |
| `AppIcon-40x40@3x.png` | 120×120 | Spotlight (Retina HD) |

**没有 `1x` 槽位，也没有 iPad 专属槽位 —— 这两条都不是遗漏。**

- 目标系统是 iOS 26（`TARGETED_DEVICE_FAMILY: 1,2`），能装它的机型**全是 @2x / @3x**，
  `1x` 槽位没有任何消费者。
- 一张 1024 就够。Apple《Configuring your app icon using an asset catalog》原文：
  「iOS, iPadOS, tvOS, and watchOS apps can auto-generate all icon variations from a
  single 1024×1024 pixel image」，同一页还写「if you have an existing project that
  provides multiple variants, consider providing a single size when that is all your
  icon requires」。
- iPad 图标现在就是这么来的：构建日志里的
  `assetcatalog_output/thinned/AppIcon76x76@2x~ipad.png` 是 Xcode 自己从 1024 生成的。

### 为什么不能写 `idiom: "ipad"`

`Contents.json` 里其它条目是 `idiom: "universal"` + `platform: "ios"`；凡是写成
`idiom: "ipad"` 的，actool 会记进 **「AppIcon has N unassigned children」**，N 正好等于
这类条目的个数 —— 也就是说它们**被忽略**。四个提交里的对应关系：

| 提交 | 条目 | 其中 `idiom: "ipad"` | 1x 槽位 | CI 实测 N |
|------|-----|----------------------|---------|-----------|
| `63decaa` | 12 | 3 | 3 | 3 |
| `ad02a88` | 9 | 2 | 0 | **2** |
| `fe4e36f` | 9 | 2 | 0 | 2 |
| `28b9e1b` | 10 | 3 | 1 | 3 |

`ad02a88` 那一步是判决点：那一轮把**三个 `1x` 槽位全部删掉**，若成因是 1x，N 应归 0；
它却只是 3 → 2，正好剩两条 `ipad` —— 所以成因是 `idiom`，不是 1x。`63decaa` 时两种
解释都恰好等于 3，这正是当初误判成「1x 槽位」的原因（见 `REDESIGN-STATUS.md` §10.6）。

三套外观的写法（2026-09-25 起）：同一槽位追加三个条目，深色 / 着色那两条多一个
`"appearances":[{"appearance":"luminosity","value":"dark"|"tinted"}]`，`filename` 指向带后缀的 PNG。
这个格式是照着**真实 Xcode 生成的 appiconset** 核的，不是照印象写的。

## 六、生成方法

### 唯一入口

```bash
# 依赖只有 Pillow（不需要 ImageMagick / cairosvg）
pip3 install Pillow
bash generate_appicon.sh
```

`generate_appicon.sh` 一条命令做两件事：① 用 `generate_appicon_pillow.py` 渲染 21 张，
直接写进**出包的那份** appiconset；② 顺手跑 `python3 scan/iconcheck.py` 自查（PNG 与
`Contents.json` 是否还一致）。

> **为什么只剩 Pillow 这一条路**（2026-09-25 改）：上一版先找 ImageMagick、找不到再退回
> `python3 generate_appicon.py` —— 而**那个文件根本不存在**。也就是说，文档承诺的退路是一条死路，
> 而它只有在「这台机器没有 ImageMagick」时才会被走到。更根本的是：ImageMagick 只能渲 SVG，
> 而 SVG 里只有浅色一套外观 —— 用它刷新会得到「一半是新图、一半是旧图」的图标集，
> 正是这个仓库记过的那个坑（**改了 A、真机上看到 B**）。所以现在 SVG 只是矢量对照，
> 出包的那一份永远由 Pillow 脚本渲染。

### 关于 `AppIcon.svg`

`AppIcon.svg` 是 v2.x 的**矢量对照**，不是可出包的源：它只有浅色一套外观，也没有深色 / 着色。
它存在的意义是「想看清几何时有一张能缩放的图」；任何一个形状常量改了，两边都要改。

### 放置位置

```
CarKeeper/CarKeeper/Resources/Assets.xcassets/AppIcon.appiconset/
```

**只有这一份 appiconset 会进包。** 仓库根目录历史上出现过的另一份 `AppIcon/` 已删 ——
两份并存时，改了不出包的那一份，谁都看不出来。这也是 `scan/iconcheck.py` 判据 5
（「目录里不许有没人引用的 PNG」）的由来。

## 七、圆角规范

iOS AppIcon 用 Squircle（超级椭圆）圆角遮罩，**由系统添加**。

- 图里**不要**自己画圆角、不要内缩、不要留透明边 —— 你自己裁一刀，系统还会再裁一刀，
  成品会比旁边系统图标小一圈。
- 也不要在边上留 4% 的空白：那是 macOS 图标的习惯，不是 iOS 的。
- 唯一要做的就是把 1024×1024 铺满，模式给 `RGB`。

---

## 八、门禁：`scan/iconcheck.py`

图标不是 Swift 文件，`design` / `lintcfg` / `eol` 那些检查一条都看不到它 —— 所以单独立了一条。
五条判据，每条都当场能量出来，不靠眼睛：

1. `Contents.json` 能解析，且每个条目引用的文件真的在目录里。
2. 每个条目的**实际像素尺寸**等于它声明的大小 × scale（1024 槽位视为 1024²）。
3. 每个槽位有**三套外观**：不带 `appearances`（浅色）、`dark`、`tinted`。
4. 三张 1024 主图**满幅**：不带透明像素，且 8 个采样点（四角 + 四边中点）与各自同一行 /
   列内侧相隔 64px 处的颜色一致（上限 `EDGE_TOL = 14`）。为什么是 14 而不是 0：
   底是**渐变**，沿一条边向内 64px 本来就会变色（实测我们这两套底最多差 7），
   而 v1.0 那种内缩 4% 的图一量就是几十、四角干脆是 255。
5. 目录里没有**没人引用**的 PNG（多出来的那种文件正是「改了 A 看到 B」的来源）。

> **这条门禁为什么自己读 PNG，而不是 `import PIL`**（值得记下来）：
> 门禁都住在 `scan/`，而脚本所在目录会被放进 `sys.path`。`scan/copy.py`（文案门禁）
> 与标准库的 `copy` **同名** —— Pillow 的 XML 依赖（`defusedxml` → `xml.etree`）
> 一 `import copy` 就拿错了模块，当场 `AttributeError: module 'copy' has no attribute 'deepcopy'`。
> 也就是说：**任何在 `scan/` 里 import Pillow 的门禁都跑不起来**。
> 所以 `iconcheck.py` 自己读 PNG（zlib + 五种过滤器，只认 8-bit RGB/RGBA、非交错 ——
> 我们自己的生成器只写这一种；其它格式一律报红让人来看，不静默放行）。
> 这个解码器与 Pillow 做过逐点比对（3 张主图 × 9 个采样点，结果一致）。

## 九、视觉检查清单

- [ ] 1024×1024 主图清晰，**满幅无黑角**
- [ ] 车身居中、长高比像轿车（约 1.68），窗与轮拱是**挖空**（透出底色，不是画深色块）
- [ ] 轮子完整落在车身内（轮心 `cy + R ≤ 780`），洞里有轮毂
- [ ] 弧在车底下、不压车轮、不贴画布边
- [ ] 三套外观（浅色 / 深色 / 着色）都在，且深色是「暖近黑 + 琥珀车」
- [ ] 58px 下仍读得出是一台车（窗、轮拱、轮毂不糊成一团）
- [ ] 所有尺寸变体无失真
